## 3. 独立 JWT secret 与迁移影响

### 3.1 改动

改造前（`auth_service.py:20`）：

```python
_JWT_SECRET = settings.LLM_API_KEY or "vibebara-default-secret"
```

问题：① 复用 `LLM_API_KEY`——LLM 密钥轮换会意外令所有登录态失效，且把「LLM 调用密钥」与「身份签名密钥」职责耦合；② 硬编码兜底值人尽皆知。

改造后：

```python
_DEV_DEFAULT_JWT_SECRET = "vibebara-dev-insecure-jwt-secret-change-me"

def _resolve_jwt_secret() -> str:
    secret = (settings.JWT_SECRET or "").strip()
    if secret:
        return secret
    if settings.DEPLOYMENT_MODE == "cloud":
        logger.warning("[security] 未设置 JWT_SECRET，cloud 模式正在使用公开的开发默认密钥……")
    else:
        logger.info("[security] 未设置 JWT_SECRET，使用稳定的开发默认密钥（仅限本地开发）……")
    return _DEV_DEFAULT_JWT_SECRET

_JWT_SECRET = _resolve_jwt_secret()
```

设计要点：

- **稳定开发默认值**：留空时回退到一个**固定常量**（非随机），保证后端重启不会令已签发 token 全部失效，开发体验不变。
- **生产/cloud 告警**：cloud 模式仍用默认值 → `logger.warning` 显著提示安全风险；local 模式 → `logger.info` 轻提示。
- **停用 LLM_API_KEY**：签名密钥与 LLM 密钥彻底解耦（单测 `test_resolve_falls_back_to_stable_dev_default_not_llm_key` 显式断言不再复用）。
- 签名比较改用 `core.security.constant_time_compare`（仍是常量时间，统一口径）。

### 3.2 迁移影响（需周知）

- **切换 `JWT_SECRET` 会使所有旧 token 失效**：从「默认值」切到注入值（或轮换注入值）后，已签发 token 验签失败，**用户需重新登录**。
- 预设用户（`DAIL` / `DAIL2`，见 `main.py:_seed_default_users`）重新登录即可，无需额外迁移。
- 建议上线节奏：先在 cloud 环境注入 `JWT_SECRET` 再发布，一次性完成切换；之后非必要不轮换（轮换=强制全员重登）。

## 4. WebSocket 强制鉴权策略

### 4.1 项目级 `/ws/project/{project_id}`（强制，硬性）

改造前（`routes.py:38`）：`if token and not verify_token(token)` —— **token 为空直接放行**。

改造后强制四步校验：

1. `token` 缺失或无效 → `close(4001)`。
2. token 解析出的 `token_user_id` 必须与连接 `user_id` 一致（**防伪冒**），否则 `close(4001)`。
3. 以 `token_user_id` 为**权威身份**参与 `connect`/广播（即使二者一致，也不信任 query 值本身）。
4. **防御性多租户校验**：该用户必须是项目所属团队成员，否则 `close(4003)`。避免非成员仅凭猜测 `project_id` 订阅他人项目的 Skill 实时动态（信息泄露）。

> 第 4 步为超出「一致性校验」的额外加固，复用 `project_service.get_project_team_id` + `team_service.is_team_member`（与 REST `_check_project_access` 同源），与既有项目 REST 鉴权口径一致。

**前端影响**：无需改动。`useSkillSync.ts` 已传 `token` 与 `user_id`；登录态下二者由登录流程同源写入 `localStorage`（`authStore` 写 token、`Login.vue:24` 写 user_id），天然一致。

### 4.2 会话级 `/ws/{session_id}`（配置开关，默认不强制）

**决策：默认不强制，提供 `WS_SESSION_AUTH_REQUIRED` 开关（默认 `false`）。**

理由：

- 该端点服务于 **adapters/sessions 实时协作**（旧的多工具会话广播），**与项目 Skill 同步无关**。
- 现有前端 `useWebSocket.ts:12` 连接该端点时**只传 `user_id`/`adapter_id`，不传 `token`**。若直接强制，会立即破坏现有 sessions 功能，违反灰度原则。
- 故采用开关：
  - `false`（默认）= 维持现状放行；
  - `true` = 强制校验 token 且 `token_user_id == user_id`，**需前端在该 WS URL 上补传 token**（M4 前端分流时一并处理）。

> 待协调者拍板：sessions 协作是否仍为目标功能。若是 → M4 让 `useWebSocket` 补传 token 后置 `WS_SESSION_AUTH_REQUIRED=true`；若否（仅保留项目同步）→ 可在 cloud 配置中直接关闭/下线 sessions 相关路由。详见 §7。

## 6. 设备配对令牌：云端侧落地与 M3 待对接点

### 6.1 契约判定（依据 M0 §5.2 / 分歧 D2）

M0 已冻结：

- **双令牌分离**：Bearer Token（云端身份，只给云端）与 Pairing Token（设备配对，只给本地代理）**互不混用**；
- 配对令牌**由桌面主进程（Electron）生成并注入**「本地代理进程」与「渲染层」，**云端不签发、不持有、不下发**（拓扑事实：云端在公网、本地代理只监听 127.0.0.1，云端无法主动连本地代理；前端是唯一编排者）。

**结论：云端无需新增「签发/下发配对令牌」端点。** 据此，M2 云端侧仅落地**共享算法基线**，确保 M3 本地代理实现与云端口径一致，避免实现漂移。

### 6.2 已落地：`backend/app/core/security.py`（共享基础设施）

| 工具 | 用途 |
| --- | --- |
| `constant_time_compare(a, b)` | 常量时间字符串比较（防时序侧信道）。已在 `auth_service.verify_token` 签名比较中复用 |
| `generate_pairing_token(nbytes=32)` | 高熵（≈256bit）URL 安全 bearer 风格令牌生成；对应 M0 §5.2「pairingSecret = randomBytes(32)」，供桌面主进程（M5）/联调脚本复用 |
| `verify_pairing_token(provided, expected)` | 基于常量时间比较的配对令牌校验占位；空值一律拒绝（防空令牌绕过） |

### 6.3 M3 待对接点（本模块仅约定，不实现本地代理本体）

- 本地代理启动时，由**桌面主进程**用 `generate_pairing_token` 生成 `pairingSecret` 并注入「本地代理进程」与「渲染层（contextBridge）」。
- 本地代理对每个**写类请求**（M0 §4.6 `write-skill` 等）读取 `X-Pairing-Token`，调用 `verify_pairing_token(header, 本进程 pairingSecret)`，失败 → `401 UNAUTHORIZED`。
- 配合 **可写根白名单**（M0 §5.3，`realpath` 防逃逸）+ **仅监听 127.0.0.1**（M0 §5.4）双重约束。
- 进阶形态（挑战-响应 / `exp` 轮换）按 D2 留待后续；M3 先用 M0 冻结的「固定高熵 bearer 令牌 + 常量时间比较」。

> 注：本地代理多为纯 TS 实现，`security.py` 作为**算法基线参照**（生成强度、比较语义、空值拒绝），M3 在 TS 侧等价实现即可。
