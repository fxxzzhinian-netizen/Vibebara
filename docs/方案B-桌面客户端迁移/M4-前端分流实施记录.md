# 方案 B · M4 前端分流实施记录

> 本文记录里程碑 **M4「前端分流」** 的前端改造（仅改 `frontend/`，不动 `backend/` 与 `local-agent/`）。
>
> 上游依据：
> - `M0-解耦设计与接口契约.md`（§3 数据流时序、§5.2 双令牌、§9 对 M4 的影响、待拍板分歧）
> - `contracts/local-agent-api.md`（本地代理 7 端点 TS 类型、§9 云端协作端点 DTO）
> - `M2-评审决议与上线清单.md`（§3 M4 待办：sessions/会话 WS 补 token；§9 Windows-first / inline 资源）
>
> 核心事实（M0 §1.1）：**云端够不着本地代理 → 前端是唯一编排者**，同时持有云端 Bearer Token 与本地配对令牌。原一次性的 deploy/push/pull/import 必须由前端串成多步链路。
>
> 状态：**已实现并通过类型检查/构建**。云端 C 类编排端点（build-artifact / register-deployment / commit-pull / push 内容版 / import-content）属 M1，**当前后端尚未实现**，故编排链路以**灰度开关**收敛——web 灰度默认走旧的一次性云端端点，桌面/联调形态启用编排链。

## 2. 双 client 与运行时配置设计

### 2.1 双 client 分离（`api/client.ts`）

| client | baseURL | 鉴权头 | 目标 | 令牌来源 |
| --- | --- | --- | --- | --- |
| `cloudClient`（默认导出） | `runtimeConfig.cloudApiBase`（web 默认 `/api/v1`） | `Authorization: Bearer <token>` | 云端 FastAPI | `localStorage.vibehub_token` |
| `localAgentClient` | `runtimeConfig.localAgentBase`（默认 `http://127.0.0.1:51873`） | `X-Pairing-Token: <pairingToken>` | 本地代理 | `runtimeConfig.pairingToken`（拦截器每次实时读取，支持 M5 轮换） |

**双令牌严格分离（M0 §5.2）**：Bearer **绝不**发给本地代理；配对令牌**绝不**发给云端。默认导出 `apiClient = cloudClient`，历史 `import apiClient from './client'` 全部无改动继续走云端。

### 2.2 运行时配置（`runtime/config.ts`）

配置结构 `VibehubRuntimeConfig`：`mode`('web'|'desktop')、`cloudApiBase`、`cloudWsBase`、`localAgentBase`、`localAgentPort`、`pairingToken`、`orchestration`。

**来源优先级（高→低）**：
1. `window.__VIBEHUB_RUNTIME__`（**M5 桌面壳** 通过 preload/contextBridge 注入真实值）；
2. Vite env `import.meta.env.VITE_*`（构建期注入，分环境/灰度）；
3. 安全默认（web 灰度）：云端 `/api/v1`（走 Vite 代理/同源反代）、云端 WS 空串（回退 `window.location`）、本地代理用 **M3 dev 默认端口 `51873` + dev 配对令牌** `vibehub-dev-insecure-pairing-token-change-me`。

**派生规则**：仅注入端口未注入 base → 按端口回推 `localAgentBase`；`orchestration` 未显式设置 → 按 `mode` 推断（desktop=true，web=false）。

辅助：`isOrchestrationEnabled()`、`getPairingToken()`、`cloudWsUrl(path)`（配了云端 WS 基址直接拼，否则回退 `window.location` 推 ws/wss）。

## 3. 本地代理 client 封装（`api/localAgent.ts`）

严格对齐 `contracts/local-agent-api.md`（camelCase）。导出全部类型（`FilePayload / ResourcePayload / UnifiedSkillPackage / ...`）与调用函数：

| 函数 | 端点 | 说明 |
| --- | --- | --- |
| `health()` | `GET /local/health` | 存活/版本/平台目录探测 |
| `browse(path?)` | `GET /local/browse` | 目录浏览（空 path→盘符/根） |
| `scan({rootDir})` | `POST /local/scan` | 纯 TS 扫描已装/可导入 Skill |
| `readFolder({path,include?})` | `POST /local/read-folder` | 递归读文件（utf8/base64） |
| `writeSkill(req)` | `POST /local/write-skill` | 落盘部署产物，**顺带回 `installedHash`**（省一次 hash 往返） |
| `hash(paths)` / `hashOne(path)` | `POST /local/hash` | 统一算法目录/文件 hash（dirty 检测） |
| watch 类型 | `WS /local/watch` | 类型已封装（连接逻辑留待 M5 桌面实时 dirty 推送时接入） |

统一失败响应（`{ok:false,error}`）由 `unwrap()` 转成 `LocalAgentCallError`（携带契约错误码 `code`），便于上层分支。

> 备注：`WS /local/watch` 仅封装了消息类型，未在 M4 接管 dirty 推送——当前 dirty 仍按需用 `/local/hash` 比对（M0 §3.6 方式二）。实时 watch 订阅留 M5（桌面常驻）接入。

## 4. 编排链路（前端视角，标注每步调云端 / 本地代理）

> 仅在 `orchestration=true` 时启用；返回值刻意与旧一次性 API **同形状**，store/view 调用签名不变。

### 4.1 部署 deploy（项目 Skill，`deployProjectSkillOrchestrated`，M0 §3.1）

| 步 | 调用方 → 目标 | 端点 | 关键字段 |
| --- | --- | --- | --- |
| ① 构建产物 | 前端 → **云端** | `POST /projects/{pid}/skills/{sid}/build-artifact {tool}` | ← `contents, resources, repoHash, repoVersion, abstractSnapshot, skillId` |
| ② 落盘 | 前端 → **本地代理** | `POST /local/write-skill {deployPath,scope:"project",tool,skillId,contents,resources,overwrite,ensureGitignore:true}` | ← `installPath, installedHash`（顺带回） |
| ③ hash | （省略）| 由 ② write-skill 顺带返回 `installedHash` | 即 ③本地 hash |
| ④ 登记 | 前端 → **云端** | `POST /projects/{pid}/skills/{sid}/register-deployment {tool,deployPath,installPath,installedHash,repoHash,repoVersion,abstractSnapshot,overwrite}` | → `SkillDeploymentResponse` |

### 4.2 拉取更新 pull-update（`pullUpdateOrchestrated`，M0 §3.3）

| 步 | 调用方 → 目标 | 端点 | 说明 |
| --- | --- | --- | --- |
| ① 本地 hash | 前端 → **本地代理** | `POST /local/hash [installPath]` | 若 `exists && hash≠installed_hash && !overwrite` → 返回 `{conflict:true}` 拦截 |
| ② 取团队产物 | 前端 → **云端** | `POST /skill-deployments/{id}/build-artifact` | ← contents+resources+teamHash(repoHash)+abstractSnapshot |
| ③ 覆盖写 | 前端 → **本地代理** | `POST /local/write-skill {...overwrite:true}` | ← `installedHash`（覆盖后） |
| ④ 提交登记 | 前端 → **云端** | `POST /skill-deployments/{id}/commit-pull {installedHash,repoHash,repoVersion,abstractSnapshot}` | → `PullUpdateResponse` |

### 4.3 推送 push（`pushOrchestrated`，M0 §3.2）

| 步 | 调用方 → 目标 | 端点 | 说明 |
| --- | --- | --- | --- |
| ① 本地 hash | 前端 → **本地代理** | `POST /local/hash [installPath]` | `!exists`→返回 missing；`hash==installed_hash`→`{no_change:true}` 直接返回 |
| ② 读本地 | 前端 → **本地代理** | `POST /local/read-folder {path:installPath,include:"all"}` | ← `files[]`（文本 utf8 / 二进制 base64） |
| ③ 上传解析 | 前端 → **云端** | `POST /skill-deployments/{id}/push {currentHash,files}` | → `PushDeploymentResponse`（diff/冲突/change_items） |

### 4.4 本地状态 local-status（`getLocalStatusOrchestrated`，M0 §3.6 方式二）

- 前端 → **本地代理** `POST /local/hash [installPath]` → `dirty = exists && currentHash != installed_hash`。
- **纯本地 hash 比对，无云端往返**（dirty 判定的正确性由 M0 §7 两端 hash 位级一致保证）。

### 4.5 个人/团队仓库部署（`deployNativeSkillOrchestrated`，§3.1 变体）

- ① 前端 → **云端** `POST /skill-forge/store/{sid}/build-artifact {tool}`；
- ② 前端 → **本地代理** `write-skill`（`destPath` 有→scope=project；无→scope=platform 落平台目录）。
- 个人仓库部署不登记 deployment（与旧 `deployNativeSkill` 一致）。

### 4.6 导入 import（`importContentOrchestrated`，M0 §3.5）

- ① 前端 → **本地代理** `POST /local/read-folder {path,include:"skill"}`；
- ② 前端 → **云端** `POST /skill-forge/store/import-content {files,origin,scope,teamId?}`。

## 7. 灰度回退策略

**单一开关 `runtimeConfig.orchestration` 决定链路**：

| 形态 | orchestration | deploy/push/pull/import/browse/scan/local-status |
| --- | --- | --- |
| web 灰度（默认） | `false` | 走**旧的一次性云端端点**（`/skill-forge/browse`、`/.../deploy`、`/.../push` 等），**不触达本地代理**，现状完全不变 |
| 桌面/联调（M5 注入 mode=desktop，或 `VITE_ORCHESTRATION=true`） | `true` | 走 §4 多步编排链（云端产物 ↔ 本地代理 ↔ 云端登记） |

- 分流点全部落在 **api 层**（`projects.ts`/`skillForge.ts`/`skillStore.ts`），上层 store/view 调用签名零改动。
- 分流函数对本地代理/云端异常做了兜底（返回与旧响应同形的 `{success:false,error}`），不会因本地代理离线把 web 形态打挂（web 形态根本不进编排分支）。
- browse/scan 的本地代理响应（camelCase）经 `normalizeBrowse / normalizeScanPackage` 归一为旧 snake_case 形态，FolderPicker/Dashboard/SkillForge/Teams 调用方无感。

## 8. 对云端编排端点的依赖与对齐假设

> 以下云端 `/api/v1` 端点为 **C 类改造（M1）**，**当前后端尚未实现**。前端已按契约 §9 字段对接，标 `TODO(cloud)`，待 M1 落地后端联调。

| 前端调用 | 云端端点（待实现） | 请求体 | 期望响应 | 对齐假设 |
| --- | --- | --- | --- | --- |
| deploy ① | `POST /projects/{pid}/skills/{sid}/build-artifact` | `{tool}` | `BuildArtifactResponse` | resources 为 `transfer:"inline"`（M2 决议⑥）；abstractSnapshot 云端从产物生成（M0 §3.1/D4-A） |
| deploy ④ | `POST /projects/{pid}/skills/{sid}/register-deployment` | `RegisterDeploymentRequest` | `SkillDeploymentResponse`（复用现有 schema） | `installed_hash` 以本地代理算为权威（M0 §3.1） |

**需协调者拍板 / 待联调的点**：
1. **store 级 `build-artifact`**（个人/团队仓库部署）契约 §9 未定义，需 M1 补端点（前端已按 project 版镜像调用，字段待对齐）。
