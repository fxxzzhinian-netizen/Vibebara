## 2. 决定①：deployed_* 降级为本地代理 scan.installedAt 实时探测

### 2.1 问题

`SkillPackage.deployed_cursor / deployed_codex` 原由后端 `native_skill_store._upsert_db` 探测**后端机器** home 的 `~/.cursor|.codex/skills/{skill}/SKILL.md` 设置。薄代理/cloud 形态下后端磁盘与用户机器无关，该探测**无意义**；且「某 Skill 是否已装到本机 cursor/codex」本质是**按用户/按机器**语义，挂在全局 `SkillPackage` 上有多租户偏差（M4 后端记录 §10/§13 已列为拍板项）。

### 2.2 新展示方案（落地）

- **数据来源**：本地代理 `scan` 的 `installedAt:{cursor,codex}`——它探测**用户机器**的 `cursorSkillsDir()/{id}/SKILL.md`、`codexSkillsDir()/{id}/SKILL.md`（`local-agent/src/scan/scan.ts:125-128`），与契约 §4.3 一致。
- **前端汇总**：`orchestration.getPlatformInstalledStatus()` 先 `health()` 取 `platformSkillDirs.{cursor,codex}`，再对两个平台目录各 `scan()`，把每个包的 `installedAt` 汇总成 `{ [skillId]: {cursor,codex} }`。
- **展示分流**：
  - `SkillForge.vue` 个人 Skill 列表的安装点（deploy-dots）改用 `store.installedStatus(s)`：
    - **编排形态**（`orchestration=true`，桌面/联调）：用本地代理实时 `installedAt`；
    - **web 灰度**（`orchestration=false`）：回退云端 `deployed_cursor/codex`（旧字段展示不破坏）。
  - `Dashboard.vue` 扫描列表的安装点本就直接用 `pkg.installed_at`（scan 结果），无需改动。
- **后端**：cloud 模式 `_upsert_db` **不再据后端盘设置** deployed_*（新行默认 False、存量值不被后端盘探测覆盖）；**local 模式行为完全不变**（仍探测后端=本机 home，对单机形态有效）。字段保留兼容。

```297:316:backend/app/services/native_skill_store.py
            # 平台部署状态（deployed_cursor/codex）：
            #   - local 形态（后端=用户机器）：沿用现状，探测后端机器 home 的 ...
            #   - cloud 形态（薄代理）：后端磁盘与用户机器无关，探测无意义；... 改由本地代理 scan 的 installedAt 按用户实时回答 ...
            if settings.DEPLOYMENT_MODE != "cloud":
                row.deployed_cursor = (CURSOR_SKILLS_DIR / skill_id / "SKILL.md").exists()
                row.deployed_codex = (CODEX_SKILLS_DIR / skill_id / "SKILL.md").exists()
            else:
                if row.deployed_cursor is None:
                    row.deployed_cursor = False
                if row.deployed_codex is None:
                    row.deployed_codex = False
```

> 说明：保留「不回写云端」语义（cloud 下不据后端盘设置、前端用 scan 展示），不新增「用户×Skill×工具」安装状态表，避免 schema 变更——与 M4 后端记录 §13(1) 待办收敛为「降级为仅本地展示」。

## 3. 决定②：migrate 编排接入

### 3.1 落地

前端 `migrateSkill` 灰度分流：

- **编排形态**：`migrateSkillOrchestrated(skillId, targetPlatform)`
  1. 云端 `POST /skill-forge/store/{sid}/build-artifact {tool=目标平台}` → 目标平台 contents+resources；
  2. 本地代理 `POST /local/write-skill {scope:"platform", tool:目标平台, skillId, contents, resources, overwrite:true}` → 落到本机平台目录 `~/.{tool}/skills/{skillId}`；
  3. 不登记 deployment（与 M0 §3.1 变体一致）。
- **web 灰度**：保留旧的一次性 `POST /skill-forge/migrate`（node 直接读本机文件夹适配）。

**复用 build-artifact + write-skill，云端无需新增端点**（与决定②一致）；前端 `TODO(orchestration)` 已删除。`Dashboard.vue` 迁移调用补传 `pkg.id`。

### 3.2 语义说明（重要）

薄代理下「云端够不着本地代理」，迁移产物只能由**云端构建**。因此编排路径以 **云端 Store 中同 id 的 Skill** 为产物来源（cloud 形态下 Store 即权威）。若目标 Skill 仅存在于本机文件夹、尚未入库，`build-artifact` 会失败——此场景仍可走 web 灰度旧端点（node 读本机文件夹适配）。该取舍源自协调者「复用 build-artifact + write-skill、不新增云端端点」的决定，已在 `orchestration.ts` 注释标明。

## 4. 决定③：sessions 后端强制鉴权 + 会话 WS 强制鉴权

### 4.1 sessions REST

`backend/app/api/sessions.py` 全部 6 个端点（create/list/get/join/leave/events/delete）由 `user_id="demo-user"` 兜底改为 `Depends(get_current_user_id)`，**去掉 demo-user 兜底**，身份一律取自 Bearer token。前端 `api/sessions.ts` 走 `cloudClient`（自动附带 `Authorization: Bearer`），加鉴权对前端透明；无 token 调用一律 401。

### 4.2 会话 WS

`/ws/{session_id}` 有效鉴权判定改为：

```python
auth_required = settings.WS_SESSION_AUTH_REQUIRED or settings.DEPLOYMENT_MODE == "cloud"
```

- **cloud 形态默认强制**（满足 M2 决议①「计划强制鉴权」+ M4 收尾）；
- local 形态默认沿用现状不强制，可经 `WS_SESSION_AUTH_REQUIRED=true` 显式开启（兼容历史 sessions 协作）；
- 强制时：token 缺失/无效 → close 4001，且 token 解析的 `user_id` 必须与连接 `user_id` 一致。

> 前端先行（M4 前端分流已落地）：`useWebSocket.ts` 已在会话 WS URL 上补传 `token`，`SessionDetail.vue` 用登录用户 id——满足 M2 决议①「前端补传 token 先行、后端再开强制」的顺序。

> 项目级 WS `/ws/project/{project_id}` 为 M2 硬性强制鉴权，本次不变。
> `adapters/{id}/inbound` 外部 webhook 鉴权（M2 §3 待办）属外部入站、cloud 已下线整个 `/adapters/*` 路由，本次不处理。

| 闭环 | 步骤（orchestration.ts 顺序） | 结果（实测） |
