# M4 · 云端编排端点实施记录（后端侧）

> 范围：仅 `backend/app`（+ 测试/文档）。未改 `frontend/`、`local-agent/`。
> 对齐基准：**前端 `frontend/src/api/orchestration.ts`（权威参照）** + `M0 §9` 契约。
> 灰度：保留全部旧「一次性」端点不破坏 local 形态；新增编排端点供 cloud/桌面形态使用。

---

## 1. 背景与目标

桌面客户端形态下「**云端够不着本地代理**」（本地代理仅监听 `127.0.0.1`），故 deploy/push/pull/import
这类跨端流程改由**前端编排**串联：「云端构建产物 → 本地代理落盘/读盘 → 本地代理算 hash → 云端登记元数据」。

本里程碑把云端原先「一次性」端点（后端直接 `call_bridge` 构建 + 写后端盘 + 读后端盘算 hash）
拆出**可被前端编排的配套端点**，使云端在编排路径下：

- **构建产物不写后端盘**（产物经响应体下发，由本地代理落盘）；
- **登记/同步不读后端盘**（`installed_hash` 由本地代理实算、前端上报，云端只写库）；
- **push/import 接收上传内容**（云端在临时目录重建后复用既有业务语义，不读用户本地盘）。

### 2.1 BuildArtifactResponse（contents + resources + 版本/hash，camelCase 输出）

```jsonc
{
  "success": true,
  "skillId": "demo",
  "tool": "cursor",
  "contents": { "SKILL.md": "...", "AGENTS.md": "..." },   // 仅文本（构建产物）
  "resources": [                                            // scripts/references/assets，含二进制
    { "path": "assets/icon.png", "transfer": "inline", "encoding": "base64", "content": "...", "size": 7 },
    { "path": "scripts/run.py",  "transfer": "inline", "encoding": "utf8",   "content": "print(1)\n", "size": 9 }
  ],
  "repoHash": "<sha256>",        // = _compute_content_hash(store_path)，M1 收敛算法
  "repoVersion": 3,
  "abstractSnapshot": { ... }    // 云端从「contents+resources 临时目录」parse_native_skill 生成
}
```

资源默认 `transfer:"inline"`（M0 分歧 D1：M3 先用 inline，契约预留 `url`）。结构与本地代理
`write-skill` 接收的 `resources: ResourcePayload[]` **同形**，前端 `toWriteResources()` 直接透传。

### 2.2 请求 DTO 命名兼容

新增请求 DTO 统一 `ConfigDict(populate_by_name=True)` + camelCase `alias`，**同时接受 camelCase
（前端口径）与 snake_case（后端口径）**：

- `RegisterDeploymentRequest`：`tool / deployPath / installPath / installedHash / repoHash / repoVersion / abstractSnapshot / overwrite`
- `CommitPullRequest`：`installedHash / repoHash / repoVersion / abstractSnapshot`
- `PushContentRequest`：`currentHash / files[]`（`files` 项为 `{path, encoding:"utf8"|"base64", content}`）
- `ImportContentRequest`：`files[] / origin? / scope?("personal"|"team") / teamId?`

## 6. hash 一致性说明

- 云端 `repoHash` = `_compute_content_hash(store_path)`，即 M1 收敛后的算法：
  **相对 POSIX 路径 UTF-8 字节序排序 + sha256**，与本地代理（M3）`dirHash` 位级一致。
- 编排路径下，`installed_hash` **以本地代理 `write-skill` / `hash` 实算为准**，前端透传给
  `register-deployment` / `commit-pull` / `push`；**云端不再读用户本地盘重算**。
- 内容搬运忠实性（`backend/app/services/content_transfer.py`）：
  - `utf8` 用 `str.encode("utf-8")` 后 `write_bytes` 落盘，**不做 CRLF/LF 归一、不经文本模式换行翻译**；
  - `base64` 精确还原二进制；
  - 资源归集 `collect_store_resources` 排序键 = 相对 store 的 POSIX 路径 UTF-8 字节序（与 hash 同口径），
    保证产物顺序稳定。
- 单测 `test_write_files_faithful_and_hash_consistent` 用**独立参考实现**校验 `write_files` 落盘后的
  目录 hash 与收敛算法一致（防止换行/编码偏差破坏两端 hash）。

## 7. 鉴权与多租户

| 端点 | 守卫 | 越权表现 |
|---|---|---|
| project 级 build-artifact / register-deployment | `_check_project_access`（team 成员） | 非成员 403；项目不存在 404 |
| deployment 级 build-artifact / commit-pull / push | 服务层校验 `deployment.user_id == user_id` | 他人部署 → `success:false`（业务错误） |
| store 级 build-artifact / import-content(scope=team) | `_assert_skill_accessible`（IDOR 防护）/ 团队成员校验 | 无权 → `success:false`（与 store build/deploy 口径一致） |

`register-deployment` 仅允许登记**已关联本项目**的 Skill；`import-content` 的 `scope=team` 要求
`team_id` 且调用者为该团队成员。

## 8. 对前端编排的调用顺序（契约要点，供前端 worker 对齐）

### 8.1 deploy（项目 Skill，M0 §3.1）
1. `POST /projects/{pid}/skills/{sid}/build-artifact {tool}` → 取 `contents/resources/repoHash/repoVersion/abstractSnapshot`
2. 本地代理 `POST /local/write-skill`（覆盖语义）→ 返回 `installPath` + `installedHash`
3. `POST /projects/{pid}/skills/{sid}/register-deployment`（带 step1 的 repo* + step2 的 installPath/installedHash）

### 8.2 pull（M0 §3.3）
1. 本地代理 `/local/hash` 比对 `installed_hash`；有未推送改动且未授权覆盖 → 前端拦截 `conflict`
2. `POST /skill-deployments/{id}/build-artifact {}` → 团队最新产物
3. 本地代理 `write-skill`（`overwrite:true`）→ `installedHash`
4. `POST /skill-deployments/{id}/commit-pull`（installedHash + repo*）→ 云端 status=synced、写 change log、广播 `skill.pulled`

### 8.3 push（M0 §3.2）
1. 本地代理 `/local/hash`：不存在 → `missing`；等于 `installed_hash` → `no_change`（前端直接返回）
2. 本地代理 `/local/read-folder {path, include:"all"}` → `files[]`
3. `POST /skill-deployments/{id}/push {currentHash, files}` → 云端临时目录重建 → diff → 冲突判定 → 写回 Store → 版本 +1 → 标记其他实例 outdated → 广播 `skill.pushed`

### 8.4 import（M0 §3.5）
1. 本地代理 `/local/read-folder {path, include:"skill"}` → `files[]`
2. `POST /skill-forge/store/import-content {files, origin?, scope, teamId?}`

### 8.5 个人/团队仓库 Skill 部署（§3.1 变体）
1. `POST /skill-forge/store/{sid}/build-artifact {tool}`
2. 本地代理 `write-skill`（`scope=project|platform`）
3. 个人仓库部署**不登记 deployment**（与旧 `deployNativeSkill` 一致）

## 9. 前后端契约不一致之处及处理

| 项 | 现象 | 处理 |
|---|---|---|
| **store 级 build-artifact** | 前端 `buildArtifactForStoreSkill` 调用 `POST /skill-forge/store/{sid}/build-artifact`，但 M0 §9 未单列该端点 | 以「联通」为准**补齐该端点**，字段对齐前端 `BuildArtifactResponse`；`repoVersion` 对个人/团队仓库无项目版本语义，固定 `0`（前端该路径不登记 deployment、不消费 repoVersion） |
| **build-artifact 响应大小写** | 前端 `BuildArtifactResponse` 为 camelCase；后端其余响应（deployment/pull/push）为 snake_case | build-artifact 用 `serialization_alias` 输出 camelCase；其余复用既有 snake_case schema（与前端从 `projects.ts` 引入的类型一致） |
| **deployment build-artifact 空体** | 前端 `buildArtifactForDeployment` POST `{}` | 该路由不声明请求体模型，避免 422 |
| **migrate** | 前端暂留旧端点 + `TODO`，未走编排 | 后端**不新增** migrate 编排端点，保留旧 `POST /skill-forge/migrate`（见 §10） |
| **deployed_cursor/codex 标记** | 前端 `deployNativeSkillOrchestrated` 注释「薄代理下需云端依据本地 `scan.installedAt` 回写，此处暂不回写」，**未调用任何端点** | 前端无调用 → 后端**不自创端点**，列为待办（见 §10、§12） |

## 10. migrate / deployed 标记现状（待办说明）

- **migrate（跨平台迁移）**：M0 §5.2 / §3.1 变体定位为 deploy 的变体（云端按目标平台构建产物 →
  本地代理 `write-skill` 落到迁移目标目录，不一定登记 deployment）。前端当前**保留旧端点 +
  `TODO(cloud)`**，未串联编排。后端因此**维持旧 `POST /skill-forge/migrate` 不变**；待前端接入编排时，
  可直接复用现有 store 级 `build-artifact`（`{tool}` 选目标平台）+ 本地 `write-skill`，**无需新增云端端点**。

- **deployed_cursor / deployed_codex 平台部署标记**：原由云端 `deploy` 写库（基于后端机器
  `CURSOR_SKILLS_DIR` 探测）。薄代理形态下后端探测无意义，应由**本地 `scan.installedAt`** 决定。
  前端目前**未调用**任何回写端点（明确「此处暂不回写」）。本次**遵循「不自创前端没有调用的端点」**，
  暂不新增；并提示一个**建模待办**（见 §12 协调点）：`deployed_cursor/codex` 当前挂在
  `SkillPackage`（**全局**，非按用户），而「某 Skill 是否已装到本机 cursor/codex」是**按用户**语义，
  直接用单用户 scan 回写全局标记会产生多租户语义偏差，需协调者拍板字段归属后再落端点。

## 13. 遗留风险与需协调者拍板的点

1. **deployed_cursor/codex 归属建模**（拍板项）：标记目前在 `SkillPackage`（全局），但本机安装状态是
   **按用户**语义。需决定：是否新增「用户 × Skill × 工具」的安装状态表，或将该标记降级为「仅本地展示
   （由前端 scan 决定，不回写云端）」。定了再补回写端点。
2. **资源传输 inline vs url（D1）**：当前一律 `inline` base64。大资源（如大 assets）随产物全量内联会
   放大响应体；契约已预留 `url + sha256 + size`，切换时机待定。
3. **abstract_snapshot 生成口径（D4）**：本次采用「云端从 contents+resources 临时目录
   `parse_native_skill` 直接生成」（选项 A，deploy/pull 免本地回传）。若后续要求快照完全等同
   install 实落结果，需评估与本地代理回传方案的取舍。
4. **migrate 编排接入**：后端已具备复用条件（store build-artifact + write-skill），等前端去掉
   `TODO` 接入即可，无需后端新端点。
5. **CI 执行方式**：测试套件需**各自独立进程**执行，避免单进程连跑多次构建整 app schema 触发内存峰值。
