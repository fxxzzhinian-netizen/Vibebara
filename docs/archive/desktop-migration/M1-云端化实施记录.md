## 3. 去 `Path.home()` 说明（M1 退出标准核心）

改造前：

```python
SKILL_STORE_DIR: str = str(Path.home() / ".cowork" / "skills")
```

改造后：`config.py` 通过 `@model_validator(mode="after")` 解析路径，移除 user-home 语义：

1. `COWORK_DATA_DIR` 为空 → `backend/data`（基于 `Path(__file__).resolve().parents[2]`，Windows/Linux 通用，不依赖 home）。
2. `SKILL_STORE_DIR` 为空 → `{COWORK_DATA_DIR}/skills`。
3. 二者均可由环境变量显式注入（云端指向挂载卷/集中存储）。

> 仓库其余对 user-home 的引用（`native_skill_store.py` 的 `CURSOR_SKILLS_DIR`/`CODEX_SKILLS_DIR`）是**本地落盘能力**，按灰度并存原则保留，留 M3 下沉到本地代理。

## 4. 数据库连接池 / TLS（`database.py`）

`create_async_engine` 现接入 settings：

```python
engine = create_async_engine(
    settings.DATABASE_URL,
    echo=settings.db_echo,
    pool_pre_ping=settings.DB_POOL_PRE_PING,
    pool_recycle=settings.DB_POOL_RECYCLE,
    pool_size=settings.DB_POOL_SIZE,
    max_overflow=settings.DB_MAX_OVERFLOW,
    connect_args=_build_connect_args(),  # 仅在配置 TLS 时注入 ssl context
)
```

- `_build_connect_args()`：当 `DB_SSL_ENABLED` 或 `DB_SSL_CA` 非空时，构造 `ssl.SSLContext` 注入 aiomysql；`DB_SSL_VERIFY=false` 时关闭主机名/证书校验（自签场景）。
- 默认连接池参数与改造前硬编码值完全一致，行为零变化。

## 5. 运行模式开关与 lifespan 拆分（`main.py`）

lifespan 启动时读取 `settings.DEPLOYMENT_MODE`：

| 职责 | local 模式 | cloud 模式 |
| --- | --- | --- |
| DB 初始化 / seed 用户 | ✅ | ✅ |
| Native Skill Store 同步 | ✅ | ✅ |
| Store 文件监控（同步 + 广播） | ✅ | ✅ |
| 本地 Skill 目录自动扫描（`SKILL_SCAN_DIR`） | ✅ | ❌（跳过） |
| **本地部署 dirty 轮询**（`_deployment_poll_loop`） | ✅ | ❌（不启动） |

实现：`FileWatcherService.start(store_dir, watch_deployments: bool=True)` 新增参数。

- cloud：`await FileWatcherService.start(SKILL_STORE_DIR, watch_deployments=False)` — 仅启动 Store 监控（`_watch_loop`，对应 M0 「Store 同步/广播」），**不启动**用户本地部署目录的 dirty 轮询。该 dirty 检测在方案 B 中下沉给本地代理 `WS /local/watch`（M0 §3.6）。
- local：`await FileWatcherService.start(SKILL_STORE_DIR)` — `watch_deployments` 默认 `True`，全功能，维持现状。
- 两种模式都能正常构造启动。

CORS 同步接入桌面端来源：`allow_origin_regex=settings.ALLOW_ORIGIN_REGEX or None`，默认空=`None` 不影响现有 `ALLOWED_ORIGINS` 列表。

## 6. R2 hash 排序键收敛（必做项）

依据 M0 §7.2 冻结规范：**排序键统一为「相对 root 的 `as_posix()` 路径的 UTF-8 字节序升序」，大小写敏感、不做 normcase、分隔符恒为 `/`。**

两处函数同步改为：

```python
files = sorted(
    (p for p in root.rglob("*") if p.is_file()),
    key=lambda p: p.relative_to(root).as_posix().encode("utf-8"),
)
```

- `project_service._compute_content_hash`（云端 Store 侧 hash）
- `native_skill_store._compute_dir_hash`（资源/目录 hash）

**两处算法位级一致**，且与 M0 §7.3 的 TS 可复刻伪代码对齐（本地代理 M3 实现需位级复刻）。

### 收敛动机

改造前 `sorted(Path对象)` 用平台相关的 `normcase` + OS 原生分隔符比较：POSIX 用 `/`(0x2F) 大小写敏感，Windows 小写化用 `\`(0x5C)。当文件名在分隔符字符附近分歧时（如 `ref/z` vs `refA.md`：POSIX `/`<`A`、Windows `\`>`A`），同一内容在 Linux 云端与 Windows 本地排序相反 → hash 不同 → dirty 误判。收敛后跨平台/中文名一致。

### 兼容性

install / store 目录通常无诡异文件名，对既有数据基本无影响；属契约显式化，杜绝跨平台/中文名误判。

## 7. Alembic 数据库迁移

### 7.1 结构

```
backend/
  alembic.ini                 # 配置（URL 不硬编码，由 env.py 注入）
  alembic/
    env.py                    # 异步 engine + settings.DATABASE_URL + Base.metadata
    script.py.mako            # 迁移模板
    versions/
      20260601_1640_428c03c90199_baseline_schema.py  # baseline（8 表）
```

### 7.2 env.py 要点

- URL 优先级：`alembic -x db_url=<url>` > 环境变量 `ALEMBIC_DATABASE_URL` > `settings.DATABASE_URL`。
- `target_metadata = Base.metadata`，`import app.models` 触发全部模型注册。
- online 模式用 `async_engine_from_config` + `NullPool`，`run_sync` 执行迁移；支持 offline `--sql`。
- 自动把 backend 根目录注入 `sys.path`，保证 `app` 可导入。

### 7.3 baseline 生成方式

本机 MySQL 可连，但现网 `cowork` 库已有表（由 `init_db` 建），直接 autogenerate 会得到空 diff。故**对一个空临时库 `cowork_alembic_baseline` autogenerate**，得到完整 `create_table`（8 表 + 索引 + 外键 + 唯一约束 + 枚举），随后已 `upgrade head` 验证可在全新库一次性建全、并删除临时库。baseline 与当前模型完全一致。

> 若上线环境无可连 MySQL，env.py 同样支持 offline；baseline 已是显式 `op.create_table`，不依赖运行期 introspection。

### 7.4 上线 / 日常用法

```bash
# 1) 全新云端库：直接建全部表
alembic upgrade head

# 2) 已存在且由 init_db 建过表的库（如现网 cowork）：标记为已在 baseline，不重复建表
alembic stamp head

# 3) 后续模型变更：自动生成增量迁移并应用
alembic revision --autogenerate -m "describe change"
alembic upgrade head

# 4) 临时覆盖连接串（如对空库重生成 baseline）
alembic -x db_url="mysql+aiomysql://user:pwd@host:3306/dbname?charset=utf8mb4" upgrade head
```

Windows 注意：`alembic.ini` 用纯 ASCII（configparser 以系统 locale=GBK 读取，含中文会 UnicodeDecodeError）。

### 7.5 与 init_db 的关系

- `init_db` 自动建表保留为**开发兜底**，受 `DB_AUTO_CREATE`（默认 `true`）控制；首次启动仍自动可用。
- 云端用 Alembic 管 schema 时，设 `DB_AUTO_CREATE=false` 并改用 `alembic upgrade head`，避免双写 schema。

## 11. 需协调者拍板的点 / 风险

1. **现网库 stamp**：现有 `cowork` 库由 `init_db` 建表，启用 Alembic 管控时需执行一次 `alembic stamp head`（非破坏，仅写 `alembic_version`）。本次**未对现网库执行 stamp**，避免副作用；上线切换时机请协调者确认。
2. **cloud 模式下 Store 监控去留**：当前 cloud 仍保留 `_watch_loop`（监控 `SKILL_STORE_DIR` 文件变更→同步/广播），符合 M0「保留 Store 同步/广播」。若云端 Store 改为对象存储（非本地文件系统卷），该 watch 需在 M2/M3 改为基于 API 事件触发，而非文件监听。
3. **R2 收敛对历史 dirty 基线**：收敛后排序口径变化理论上可能令极个别含特殊字符文件名的 install 目录 hash 改变，导致其首次比对呈 dirty。对常规 skill 目录无影响；如线上有历史部署，建议上线后做一次基线刷新（重新登记 `installed_hash`）。
4. **JWT secret 仍复用 `LLM_API_KEY`**（`auth_service.py:20`）：属 M2 范畴，本次未动。
5. **DB_SSL 默认值**：托管 MySQL 若强制 TLS，上线须设 `DB_SSL_ENABLED=true`（或提供 `DB_SSL_CA`），否则连接失败——需在部署清单中显式配置。
