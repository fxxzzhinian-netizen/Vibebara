> 状态：**已拍板**（§1 四项决策为协调者敲定）。本计划据此拆 M5-a/b/c + 过程待办，给出依赖顺序、退出标准、风险。M5-a 已随本计划实施（见 `M5-a-桌面壳骨架实施记录.md`）。

## 0. 一句话定位

M5 把已经「云端化 + 本地代理化 + 前端分流」的 Vibebara 装进一个 **Electron 桌面壳**：壳 = 主进程（拉起/守护本地代理、生成注入配对令牌与运行时配置、安全存储登录 token、重做一键启动）+ 渲染层（直接复用 `frontend/` 构建产物）。M5 不改云端/本地代理的核心实现，只做**封装、进程编排、注入、打包分发**。

---

## 1. 四项拍板决策（固化）

> 以下为协调者敲定结论，M5 全程以此为准，不再反复讨论。

### 决策 A：桌面壳 = **Electron**

- 依据 §3.1：现有栈全 JS/TS，本地代理为 Node 脚本，Electron 自带 Node 运行时可**直接以 `ELECTRON_RUN_AS_NODE` 拉起本地代理**，无需用户机预装 node；团队上手成本低。
- 放弃 Tauri（需 Rust、需另带 node 跑代理），其体积优势在本项目不抵迁移成本。

### 决策 B：首发平台 = **Windows**

- 延续 M2 决议⑦ / §9「Windows-first」：hash / 文件名口径以 Windows 为准；macOS NFD 归一与 notarization **推后**到覆盖 macOS 时再做。
- M5-a 壳骨架跨平台可编译，但**打包矩阵（M5-c）只做 Windows**（NSIS/MSI + 代码签名 + 自动更新）。

### 决策 C：云端对端先做 **(b) 本地 cloud demo**

- 联调阶段用「本机以 `DEPLOYMENT_MODE=cloud` 起后端」充当云端对端（如 `http://127.0.0.1:8000`、`ws://127.0.0.1:8000`），验证桌面壳注入 + 前端编排 + 本地代理三方闭环。
- **真实云端部署（托管 MySQL / HTTPS / 域名 / 对象存储）单列**，不在 M5 壳工作内，按云端运维节奏推进。
- 桌面壳的云端地址必须 **内置默认 + 可由本机配置文件覆盖**，从本地 demo 平滑切到真实云端无需改壳代码。

### 决策 D：launcher 一键启动工具在**桌面壳主进程重做**

- 背景：M2 决议② 已在 `DEPLOYMENT_MODE=cloud` **下线后端 `/api/v1/launcher/*` 路由**（在云服务器上 spawn 用户工具无意义且危险）。
- M5：在 Electron 主进程用 TS 重做 `cursor` / `codex-cli` / `codex-app` 的命令解析与启动（参考 `backend/app/api/launcher.py` 的解析逻辑），经 IPC 暴露给渲染层；前端「启动工具」入口在 **desktop 形态调用主进程 IPC**，web 形态保留旧行为或隐藏。

### 2.1 过程待办（贯穿 M5，逐步收敛）

承 `M2-评审决议与上线清单.md` §8 / §9，以下议题在 M5 过程中按需推进，**不属于某单一子里程碑的硬退出条件**，但需在 M5 结束前明确收敛：

1. **白名单「显式注册端点」评审**（决议⑤）：~~当前本地代理走「browse 即登记」可写根~~ → ✅ **已收紧（`M5-功能修复记录.md` §3）**：`/local/browse` 去登记副作用（纯只读），写盘授权绑定「用户确认选定的 deployPath 根」（write-skill 登记 + realpath/`..` 逃逸校验），**保持 7 端点冻结**。是否进一步加「显式确认可写根」端点以防御被攻陷渲染层仍待拍板（残留点）。
2. **资源传输 inline → url**（决议⑥）：M3/M4 维持 `transfer:"inline"`（base64 内联）。当大体积二进制资源使 base64 +33% 膨胀 / `--max-body-mb` 上限压力显现时，切云端对象存储 + 本地代理「带 Bearer 下载并校验 sha256 落盘」（契约 `url` 字段已预留，无需改契约签名）。属云端 + 本地代理协同，桌面壳侧只需保证 Bearer 可达。
3. **migrate「先入库再迁移」UI**（M4-收尾遗留）：薄代理下迁移产物只能由云端构建，故跨平台迁移要求目标 Skill **已入库（Store 权威）**。需要桌面端补「先入库再迁移」的引导 UI（仅存在于本机文件夹、未入库的 Skill 先走导入再迁移），避免直接调 `migrateSkillOrchestrated` 在未入库时报错。

## 3. 依赖顺序

```
M3（本地代理，已）─┐
M4（前端分流，已）─┴─▶ M5-a 壳骨架（可运行，含注入/进程管理/令牌/safeStorage/launcher/deviceId 预留）
                              │
                ┌─────────────┴──────────────┐
                ▼                              ▼
   M5-b 平台安装态多机持久化            M5-c Windows 打包+签名+自动更新
   （依赖「持久化设计」定稿，          （依赖签名证书到位；可与 M5-b 并行，
     落最终 deviceId / 设备模型）        但发布前需对齐 M5-b 的设备身份）
                └─────────────┬──────────────┘
                              ▼
                   M5 收尾（过程待办 1/2/3 收敛 + 验收 Checklist）
```

关键依赖说明：

- **M5-a 不依赖 M5-b/c**，可独立运行联调（决策 C 的本地 cloud demo）。
- **M5-b 阻塞「最终 deviceId / 设备模型」**：M5-a 只用本机持久临时 uuid **占位**，不自创最终设备模型（见 §6）。
- **M5-c 的签名证书申请是长周期外部依赖**，须**与 M5-a/b 并行启动申请**（见 §5）。
- M5-b 与 M5-c 技术上可并行，但**正式发布前**需对齐：安装包内的设备身份初始化要符合 M5-b 定稿方案。

## 4. 各子里程碑退出标准

### M5-a 退出标准（本次已达成，详见实施记录）

- [ ] `desktop/` 可 `npm install` 且 `npm run build`（TS 编译）通过、`npm start` 可启动壳。
- [ ] 主进程启动时拉起 `local-agent` 子进程：自动探测空闲端口、注入高熵配对令牌（env）、`GET /local/health` 探测就绪；进程崩溃能按退避重启；应用退出能清理子进程（无僵尸 node）。
- [ ] 渲染层能读到 `window.__VIBEBARA_RUNTIME__`，字段与 `frontend/src/runtime/config.ts` 的 `VibebaraRuntimeConfig` 一致；前端 `getRuntimeConfig()` 走 desktop 分支（`mode='desktop'`、`orchestration=true`、`localAgentBase`=分配端口、`pairingToken`=注入值、`cloudApiBase/cloudWsBase`=本地 cloud demo）。
- [ ] 登录 token 用 Electron `safeStorage` 加密持久化（替代 localStorage），经 preload/IPC 暴露给渲染层；**web 形态保持 localStorage 不变**。

- [ ] `deviceId` 在运行时配置中预留（本机持久临时 uuid 占位），并在文档标注「最终模型待与持久化设计对齐」。
- [ ] **最佳验证**：本机 `DEPLOYMENT_MODE=cloud` 起后端 + 桌面壳跑通一次 deploy 编排闭环（build-artifact → write-skill → hash → register-deployment）；环境受限时退化为分层验证并记录手动步骤。

## 5. 风险与缓解

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **签名证书长周期** | Windows 代码签名（尤其 EV）证书申请 + 组织验证耗时数周，是 M5-c 的外部阻塞 | **立即并行启动证书申请**（与 M5-a/b 同步进行）；先用无签名内测包验证打包链路，证书到位后切正式签名 |
| 本地代理端口漂移 | 崩溃重启 / 端口被占导致 `localAgentBase` 与注入值不一致 | 重启复用同一已探测空闲端口；解析本地代理监听日志拿真实端口；重启后经 IPC 向渲染层推送更新（M5-a 先固定端口，文档登记） |
| 注入时序 | 运行时配置依赖本地代理实际端口，必须在窗口加载前就绪 | 主进程**先**拉起代理 + 健康探测，**再**创建窗口；preload 同步 IPC 取已就绪配置后 `contextBridge` 注入 |
| token 同步读取 | `safeStorage` 跨进程为异步，而前端拦截器/路由守卫同步读 token | preload 启动时同步取一次缓存进渲染层，写时同步更新缓存 + 异步落盘；前端 `tokenStorage` 按形态选择 |
| 设备模型自创风险 | M5-a 若擅自定最终 deviceId 模型，会与 M5-b 持久化设计冲突 | M5-a 只用本机持久临时 uuid 占位，**预留接口不定型**，最终由 M5-b 决定（见 §6） |
| 客户端×云端版本错配 | 客户端旧版连新云端 API | API 版本化；客户端启动校验最低兼容版本 + 自动更新（M5-c） |
| 资源 base64 膨胀 | inline 大二进制撑爆 `--max-body-mb` | 过程待办 2：切对象存储 `transfer:"url"` |
| Electron GUI 无显示环境 | CI/无头环境无法启动 Electron 窗口做 GUI 联调 | 分层验证：编译 + 本地代理管理 smoke + 后端×代理闭环（`test_e2e_orchestration.py`）替代；GUI 联调在真实桌面手动执行并记录 |

## 6. 与「平台安装态多机持久化设计」的对齐点（重要）

> 该设计已产出：[`M5-平台安装状态-多用户多机设计.md`](./M5-平台安装状态-多用户多机设计.md)（设计稿，待评审）。下列对齐点其结论已收敛如下，M5-b 实施据该设计落地：

- **最终 `deviceId` / 设备身份模型**：M5-a 在运行时配置预留 `deviceId`（可选），值为本机持久临时 uuid（存 `safeStorage`/配置文件）。→ 收敛：占位 uuid 升格为 `clientUuid`，登录后调 `POST /api/v1/devices/register` 由**云端服务端铸造规范 `device_id`** 并回写本机（设计 §3.1/§3.3）。
- **平台安装态的持久化与多机同步**：当前 `deployed_*` 已降级为本地代理 `scan.installedAt` 实时探测（M4 决定①）。→ 收敛：新建 `user×device×skill×tool` 维度的 `platform_skill_installs` 表，经前端中转上报对账；`deployed_*` 退役为派生/展示兜底（设计 §2/§4/§7）。
- **是否需要「设备注册」云端端点**：与 M2 决议④「云端不签发配对令牌」边界并存。→ 收敛：**需要** `POST /api/v1/devices/register`，但它只铸造云端设备身份、**不签发配对令牌**，与配对令牌（桌面注入、本机写盘授权）、Bearer（身份）三者职责切分（设计 §3.4）。
